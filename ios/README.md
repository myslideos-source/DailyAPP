# dayli — native iOS shell + Home Screen widget

This directory holds a **native iOS wrapper** around the dayli PWA, added
solely so dayli can carry a real WidgetKit Home Screen widget — something
no PWA can ever host, on any browser or OS. It does **not** replace the
PWA: the web app at the project root is unchanged and keeps working
exactly as before, in every browser, for anyone who doesn't install the
iOS app.

Everything in here was generated/written without Xcode or a Mac available
in the environment that produced it, so **none of it has been opened,
built, or run in Xcode, and the widget has not been tested on a real
device or simulator.** The steps below are what's left to actually get it
running — they require a Mac with Xcode and a paid Apple Developer
account (Developer Program membership, for App Groups + a real device;
the simulator can run without one but a Home Screen widget only usefully
shows on a real phone).

## What's already here

- `ios/App/` — a real Xcode project (`App.xcodeproj`), generated by
  `npx cap add ios` (Capacitor's official iOS platform template). It uses
  Swift Package Manager for its Capacitor dependencies (`CapApp-SPM/`),
  not CocoaPods, so there's no `pod install` step.
- `ios/App/App/Info.plist` — already has the `dayli://` custom URL scheme
  registered (`CFBundleURLTypes`), so deep links work as soon as you build.
- `ios/App/App/Plugins/DayliWidgetBridgePlugin.swift` — a custom Capacitor
  plugin (Swift-only registration, no `.m` bridge file needed) that the
  web app calls to write the widget's data snapshot. Not yet added to the
  Xcode target — see step 5.
- `ios/DayliWidget/` — the WidgetKit extension's Swift source
  (`DayliWidgetSnapshot.swift`, `DayliWidgetProvider.swift`,
  `DayliWidgetViews.swift`, `DayliWidget.swift`) and `Info.plist`. This is
  **not** a buildable Xcode target yet — Xcode has to generate the actual
  extension target (its own bundle ID, product type, embed-in-host build
  phase, entitlements) via its own UI; hand-editing `project.pbxproj` to
  fake that is exactly the kind of "looks done but isn't" shortcut this
  was built to avoid. Step 3 below adds the real target, then you drop
  these files into it.
- `capacitor.config.ts` (repo root) — points the native shell at dayli's
  deployed production URL (`server.url`) rather than a bundled static
  export, so the native app and the browser PWA are always the exact same
  build. **Replace the placeholder URL before building** (step 2).
- Web-side integration (already wired into the Next.js app, needs no
  further work): `lib/native/widget-bridge.ts`, `lib/widget-snapshot.ts`,
  `lib/hooks/useWidgetSnapshotSync.ts`, `lib/hooks/useDeepLinks.ts`, called
  from `components/layout/AppShell.tsx`.

## Setup steps

### 1. Install prerequisites (on a Mac)

- Xcode 16+ (for the `containerBackground(for: .widget)` API and current
  WidgetKit families) from the Mac App Store.
- An Apple Developer Program membership (developer.apple.com) — required
  for App Groups, which the widget cannot work without.

### 2. Point the app at dayli's real URL

Edit `capacitor.config.ts` at the repo root and replace
`https://REPLACE-WITH-DEPLOYED-DAYLI-URL.example.com` with dayli's actual
deployed origin (wherever the Next.js app is hosted). Then, from the repo
root:

```sh
npm install
npx cap sync ios
```

`cap sync` copies the config into the native project and updates the SPM
plugin manifest — run it again any time `capacitor.config.ts` or the
Capacitor npm packages change.

### 3. Open the project and add the Widget Extension target

```sh
open ios/App/App.xcodeproj
```

In Xcode: **File → New → Target… → Widget Extension**.

- Product Name: `DayliWidget` (must match the `kind` string used
  throughout the code, `"DayliWidget"`).
- Team: your Apple Developer team.
- Bundle Identifier: `com.dayli.app.DayliWidget` (must be the host app's
  bundle ID, `com.dayli.app`, plus a suffix — required by Apple for
  extensions).
- **Uncheck** "Include Configuration Intent" (this widget doesn't need a
  user-configurable App Intent for v1 — see spec §17, interactivity is
  explicitly deferred).
- When asked whether to activate the new scheme, choose **Activate**.

Xcode generates a template `DayliWidget/` group with its own
`DayliWidget.swift`/`DayliWidgetBundle.swift` and `Assets.xcassets`. Delete
the **generated Swift files** (keep the generated `Assets.xcassets` and
`Info.plist` if you prefer Xcode's, or replace `Info.plist` with the one
in this repo's `ios/DayliWidget/` — either works, they're equivalent), then
drag the four `.swift` files from this repo's `ios/DayliWidget/` into the
new target's group in Xcode (make sure "DayliWidget" is checked under
Target Membership for each).

### 4. Configure the App Group (both targets)

The app and the widget extension share data through an App Group — this
is the "clean native data exchange" the widget can't get any other way
(they're separate processes with separate sandboxes).

For **both** the `App` target and the `DayliWidget` target:

1. Select the target → **Signing & Capabilities** → **+ Capability** →
   **App Groups**.
2. Click **+** and add a new group with the exact identifier
   `group.com.dayli.app` (this string is hard-coded as
   `DayliWidgetStore.appGroupId` in `ios/DayliWidget/DayliWidgetSnapshot.swift`
   — if you use a different group ID, change it there too, in both
   targets' entitlements).
3. Make sure the **same** group is checked on both targets — Xcode
   creates a separate `.entitlements` file per target automatically; you
   don't need to create these by hand.

### 5. Add the widget-bridge plugin and shared model to the app target

1. In Xcode, add `ios/App/App/Plugins/DayliWidgetBridgePlugin.swift`
   (already in the repo — check it's part of the `App` target; drag it in
   if Xcode doesn't pick it up automatically) to the **App** target.
2. `DayliWidgetSnapshot.swift` (in `ios/DayliWidget/`) has to be compiled
   into **both** targets, since it defines the shared JSON model and the
   App Group file path. Select the file in Xcode's file navigator, open
   the File Inspector (right sidebar), and check **both** "App" and
   "DayliWidget" under Target Membership.
3. Build (`Cmd+B`) — Capacitor's Swift Package Manager plugin loader
   picks up `CAPBridgedPlugin`-conforming classes automatically; no manual
   plugin registration list to edit.

### 6. Signing

- Select the `App` target → **Signing & Capabilities** → set your Team,
  let Xcode manage the provisioning profile ("Automatically manage
  signing").
- Repeat for the `DayliWidget` target — it needs its own provisioning
  profile (extensions are signed separately from their host app), which
  Xcode generates automatically once the Team is set and App Groups is
  configured on both.
- A physical iPhone (Settings → General → VPN & Device Management → trust
  your developer certificate) is needed to see the widget on an actual
  Home Screen; the Simulator can run the app but Home Screen widgets are
  far more representative on a real device.

### 7. Build, run, add the widget

1. Run the `App` scheme on your device (`Cmd+R`).
2. Sign in as Domenico or Elisabeth inside the app once — this triggers
   the first `writeSnapshot` call (see `lib/hooks/useWidgetSnapshotSync.ts`),
   which populates the App Group container.
3. On the device: long-press the Home Screen → **+** → search "dayli" →
   add the small or medium widget.
4. Edit an event or task in the app, background it (Home button/swipe up)
   and back — the widget should update within a few seconds
   (`WidgetCenter.shared.reloadTimelines` is called on every snapshot
   write; iOS still decides the actual redraw timing, per Apple's
   documented WidgetKit budget — this is not instant/real-time by design,
   see spec §12).

### 8. App Store considerations (not needed for local testing)

- The widget extension needs its own entry under **App Store Connect** →
  your app record when you eventually submit — Xcode's archive/upload
  flow includes it automatically once it's a proper target with a valid
  bundle ID nested under the host app's.
- `com.dayli.app` and `com.dayli.app.DayliWidget` are placeholders picked
  for this project; if dayli is ever actually published, register the
  real bundle IDs and App Group in the Apple Developer portal
  (Certificates, Identifiers & Profiles → Identifiers) before the first
  TestFlight/App Store build, matching whatever you set in steps 3–4.

## What still isn't done after these steps

- **Interactive widget actions** (ticking a task off from the widget
  itself) — spec §17 explicitly defers this; the data model
  (`WidgetTask.isCompleted`) is ready for it, but no `AppIntent` exists
  yet.
- **Real logo asset** — `DayliWidgetViews.swift` renders a plain text
  "dayli" wordmark; the actual PNG/SVG logo (`public/brand/logo.png` in
  the web app) was never converted into an `Assets.xcassets` image set,
  since that's a binary-asset step best done in Xcode's asset catalog
  editor rather than scripted blind.
- **Android** — none of this touches Android; dayli's Android story is
  still "open the PWA in Chrome / install to Home Screen", unchanged.
